## Commands

```bash

./run.sh                                          # starts the daemon (sources .env automatically; runs `python -m crt.daemon`)
crt-tui                                           # console script: Textual TUI client; talks HTTP to the daemon
CRT_DAEMON_URL=http://chet.<tailnet>.ts.net:8765 crt-tui    # target the production daemon over Tailscale

# Tests
source .venv/bin/activate
python -m pytest tests/ -v                        # full unit suite
python -m pytest tests/test_library_store.py -v   # single file
python -m pytest tests/test_pipeline.py::test_fetch_title -v  # single test

# Integration tests (require real Chromecast + internet)
source .env.integration                           # set TEST_CHROMECAST_NAME, TEST_VIDEO_URL_1, etc.
python -m pytest -m integration -v -s             # runs tests/test_integration.py

# Dependencies
pip install -r requirements.txt                   # inside .venv

# Flipper FAP (subproject in flipper_app/, opt-in — Flipper Zero remote)
cd flipper_app && ufbt              # build → dist/crt_remote.fap
cd flipper_app && ufbt launch       # flash + run on Flipper via USB
```

External dependency: `ffmpeg` must be installed (`brew install ffmpeg`).

## Architecture

Client/server. A headless **daemon** (`crt/daemon.py`, started by `./run.sh` or `crt-daemon`) does all the work — YouTube playlist sync, download, ffmpeg encoding to 4:3 PAL (768x576, 25fps), playback on the Chromecast through our own receiver page. A **Textual TUI client** (`tui_client/`, run via `crt-tui`) is a thin HTTP consumer of the daemon's API (`crt/api.py`). The Flipper FAP + bridge are a parallel control surface — see [flipper_app/CLAUDE.md](flipper_app/CLAUDE.md).

**Data flow (in-daemon):** `SyncEngine` (`crt/sync_engine.py`) pulls the YouTube playlist into `LibraryStore` -> `PipelineWorker` (`crt/pipeline.py`) picks queued items -> yt-dlp downloads -> ffmpeg encodes -> `PlayerCore` (`crt/player_core.py`) sends `load` to the receiver page -> the page reports `ended` -> `watch_natural_end` advances the cursor to the next playable item.

**Daemon threading model:** single asyncio event loop in `crt/daemon.py` hosts `PipelineWorker` + `PlayerCore` (`crt/player_core.py`) + FastAPI app (via uvicorn). Blocking work (yt-dlp, ffmpeg, every pychromecast call) goes through `asyncio.to_thread()`. The same uvicorn instance on `:8765` serves the receiver page, its event stream and the encoded MP4 files to the Chromecast.

**Client/daemon contract:** TUI client (`tui_client/ui.py`) calls the daemon via `DaemonClient` (`tui_client/data_provider.py`, httpx). All `action_*` handlers wrap the blocking httpx call in `asyncio.to_thread` so Textual's loop stays responsive. The HTTP surface (`GET /status`, `GET /library/items`, `POST /control/{next,prev,toggle,stop,loop/toggle,sync,calibrate}`) is shared with the Flipper bridge — see "Production deployment". `/status.player` carries `state` (`idle|playing|paused|calibrating`), `current_time_s`, `duration_s`, `menu_open` (screen on the TV), `screen` (`paused|stopped|none`) and `selected_video_id` (the highlighted row, null when no screen).

**Receiver page and teletext screen:** playback runs in our page `crt/receiver_page/index.html` (a main `<video>`, a muted `<video id=preview>`, a snow canvas, the teletext grid), opened on the Chromecast by `ChromecastManager.launch_receiver` through DashCast (`load_url(url, force=True)`). The daemon talks to it over SSE (`GET /receiver/events`) and the page answers with `POST /receiver/report`; `ReceiverChannel` (`crt/receiver.py`) is the daemon end and keeps a local model of the page's position. Every pause, and the stopped state with the page open, shows the full-screen teletext screen (`crt/screen.py`, pure logic; `PlayerCore.screen`; the `screen{view}` message carries the whole view, the font is served at `GET /receiver/bedstead.otf`): a playlist page of rows plus two command rows (video: Riprendi/Elimina/Stop; player: Calibra/Loop/Sync/Spegni). `next`/`prev` move the highlighted row, `seek/*` move along the command row, `toggle` runs the selected command; Up/Down show the row's muted preview (`{id}_pal_..._noaudio.mp4`, an audio-less remux made by `make_preview` after each encode and backfilled at daemon start by `PipelineWorker.backfill_previews`; the sync removal and the deletions both go through `QueueItem.delete_files`, which also removes the original download, and `cleanup_temp_files` keeps it with its video). `blank{}` only unloads the main video and stops the calibration; the screen is its own `screen{view}` message (`view: null` hides it). Stop sends `blank` then the stopped screen, so the TV stays on the teletext page with the app open. After `NIGHT_AFTER_S` (5 min) without keys the screen goes into a night phase: navigation keys (`prev`, `next`, `toggle`, `seek/*`) only wake it (ack `woke`); explicit commands (`stop`, `delete/current`, `calibrate`, `loop/toggle`, `sync`, `play/{id}`) wake it and act. Two kinds of notice: "Non ancora pronto" and the loop/sync/calibration/media-error notices are row-18 flashes for `NOTICE_S` (2 s; the media error stays until a key); "Fine della coda" and "Video rimosso dalla playlist" are row-4 arrival notices for `ARRIVAL_NOTICE_S` (5 s), shown over the paused time too. Both clocks start when the page is connected. `Spegni` (`power_off`) and the idle close send `blank` + `screen{view: null}` and then close DashCast (`quit_app` swallows its timeouts, so a page left open is empty instead of an awake screen the daemon no longer tracks), both through `_close_app`: a launch asked before it gives up (`_app_epoch`), one asked after waits for the quit (`_app_lock`), and a page being quit doesn't count as open; the next navigation key reopens the stopped screen (ack `launching`). `stop`/`stop_and_remove` never relaunch a closed page. An open screen redraws on library changes (`PlayerCore.refresh_screen`, wired to the pipeline's update callback and `SyncEngine(on_synced=...)`). The Flipper and the bridge are unchanged; the daemon reinterprets the endpoints. Design: [docs/superpowers/specs/2026-11-08-teletext-screen-design.md](docs/superpowers/specs/2026-11-08-teletext-screen-design.md) (supersedes the 2026-11-07 pause-menu design).

**Configuration:** Environment variables loaded from `.env` via `run.sh`. Config constants in `config.py`. Key env vars:
- `CRT_SCALE_MODE` (`crop`|`pad`, default `crop`) — crop fills the frame by cutting edges, pad adds letterbox bars.
- `CRT_MARGIN_TOP`, `CRT_MARGIN_BOTTOM`, `CRT_MARGIN_LEFT`, `CRT_MARGIN_RIGHT` (pixels in logical 768×576 frame, default 0) — black borders to compensate for CRT overscan. Sum per axis is clamped to 50% of the frame. Press `Ctrl+T` in the TUI to show a calibration grid. The teletext screen on the TV is inset by the same margins. Changing any margin triggers re-encode (cache filename carries `_m{t}-{b}-{l}-{r}` suffix when non-zero).
- `CRT_AUTO_CROP` (`1`|`0`, default `1`) — when enabled, `_detect_crop()` analyzes the first 120 frames for baked-in black bars and applies a `crop=...` before encoding. Set to `0` to skip it entirely. Useful when cropdetect misfires on videos with dark content near the edges (opening titles, night scenes), which can silently delete real pixels before the margin step.
- `CRT_LOOP` (`1`|`0`, default `0`) — when enabled, the playlist loops back to the first item after the last item finishes. Togglable at runtime via `Ctrl+R` in the TUI (session-local, not persisted to state.json).
- `CRT_SAVE_INTERVAL_S` (seconds, default `30`) — how often the daemon persists state to disk via the `periodic_save_loop` background task in `crt/daemon.py`. State is no longer saved only on graceful shutdown, so a crash/OOM/reboot now loses at most one interval of cursor/loop_mode/playback_position changes. The shutdown path keeps its own final flush.
- `CRT_RECEIVER_IDLE_CLOSE_S` (seconds, default `1800`) — after this long stopped or paused, counted from the last key on the screen (library redraws don't reset it), `PlayerCore.watch_idle` saves the position and closes the DashCast app. The next play reopens it (logo) and resumes from the saved position.

**Persistence:** Queue state (items, history, playback position) saved to `~/.local/share/crt-player/state.json` (configurable via `CRT_STATE_FILE`). `periodic_save_loop` persists every `CRT_SAVE_INTERVAL_S` (default 30s) **and** on graceful exit (issue #4 — a hard kill no longer loses the cursor). `save_state(path, playback_position=X)` writes the live position onto the cursor item before serializing so a restart resumes from the pause point. On reload, mid-processing items reset to `"queued"`; playing items become `"ready"` if encoded file exists (skips download+encode).

**Control acks:** `POST /control/{next,prev,toggle,stop,play,seek/*}` return a structured ack `{"ok": true, "did_action": bool, "reason": str|null, ...}` (issue #6). `PlayerCore` methods return an `ActionResult(did_action, reason)`; `api.py`'s `_ack()` translates it. `reason` ∈ `{no_items, no_playable_item, cursor_unchanged, no_chromecast_session, already_stopped, woke, launching, null}`; `launching` is a performed action whose page is still opening in the background (a failed launch only logs and goes idle), also returned by a key that opens the closed page even if its own action did nothing; `woke` is performed: the key only woke the night phase and its own action did not run; `already_stopped` is a stop while stopped. A no-op (e.g. nothing ready to play, OK on a row not ready yet, or a seek on the stopped screen with nothing to move) is now `did_action=false` instead of an indistinguishable 200 OK. **Follow-up (separate repo):** the `crt-flipper-bridge` should log `did_action=false` at WARN — not yet done.

**Playlist model:** `done` is informational only — not a terminal state. `PlayerCore` moves the cursor by queue position with `_find_playable_index()`, which lands only on items whose encoded file exists (re-queueing stale ones, issue #10) and wraps when `loop_mode=True`. `LibraryStore.advance_cursor()` / `prepare_for_play()` served the old pipeline cast loop and have no caller left.

**Failed downloads are retried by the sync (issue #14):** an `error` item never has a `filename`, so the missing-cache reconcile can't see it. `SyncEngine._apply_diff` re-queues it at the next sync, then waits 10 min, 20, 40… up to 6 h between retries (`RETRY_BACKOFF_BASE_S`/`RETRY_BACKOFF_MAX_S`). The backoff lives in memory: a daemon restart retries every `error` item at the first sync, and removing a video from the playlist forgets its count.

**Encoding pipeline:** `_detect_crop()` runs a cropdetect pre-pass (120 frames) to remove baked-in black bars from the source. `_build_video_filter()` then applies scale+crop or scale+pad based on `CRT_SCALE_MODE`, and stretches the result to 16:9 (1024x576) so the Chromecast doesn't add pillarboxing — the user's HW squeezes 16:9→4:3 restoring correct proportions.

**Encoding cache:** Cached files are named `{video_id}_pal_{scale_mode}.mp4` in TEMP_DIR (back-compat shape; when any `CRT_MARGIN_*` is non-zero the name gains a `_m{top}-{bottom}-{left}-{right}` suffix). Changing `CRT_SCALE_MODE` or any margin triggers re-encode. The filename helper lives in `crt/config.py` as `cached_encoded_filename()` so `crt/pipeline.py` and `crt/library_store.py` agree. At daemon start, `cleanup_temp_files(library)` (run after `load_state`) deletes files older than `FILE_TTL_HOURS` (default 24h) that no library item refers to (`filename`, canonical encoded name, `downloaded_path`); files of videos still in the playlist are kept however old (issue #16). A video leaving the playlist has its files deleted by the sync, and `PipelineWorker.cancel_prepare_for(video_id)` (called from the daemon's `on_remove`) stops its encode if it is the one in progress; a download in progress can't be interrupted (yt-dlp runs in a thread) and is dropped when it finishes. A cancelled encode deletes its partial output, which the cache check would otherwise take as ready (issue #17). `fetch_title()` returns `(title, video_id, duration)`: `_prepare_one` fills `QueueItem.duration` (0 while unknown) from that metadata or the download's only while unknown, and once the video is ready reads it with ffprobe from the encoded file, which wins (yt-dlp said 411 s for a 410.5 s file); `PipelineWorker.backfill_durations` probes at daemon start the cached files that have none. The teletext rows' right column and row 4 read it (rule in the spec's "Righe dei video").

**Queue helpers:** `can_move(item_id, direction)` returns bool for UI disabled state. `first_queued_after_cursor()` is used by the prefetch loop to skip items before the cursor.

## Production deployment (Chet + Lodge)

Split-host since 2026-05-22: the daemon runs in Docker (`lodge-crt-player`) on **Chet** (Linux Mint); the Flipper bridge (`lodge-crt-flipper-bridge`) stays on **Lodge** (Raspberry Pi 5, whose BT adapter sees the FAP) and POSTs to the daemon over the tailnet. Both are deployed from the sibling `homelab` repo, the source of truth for ops: [`../homelab/services/crt-player/CLAUDE.md`](../homelab/services/crt-player/CLAUDE.md) (config, backup, ops gotchas) and [`../homelab/services/crt-flipper-bridge/CLAUDE.md`](../homelab/services/crt-flipper-bridge/CLAUDE.md). Integration spec: `../homelab/docs/superpowers/specs/2026-05-11-crt-services-integration-design.md`.

**Container layout:** `network_mode: host` (mDNS Chromecast discovery + direct MP4 stream require multicast/no-NAT), `cpus: 2.0` + `cpu_shares: 256` (ffmpeg deprioritized vs the host's other services). Bind mounts: `/opt/lodge/crt-player/{cache,state,secrets}` → `/data/{cache,state,secrets}`. **`secrets` mount is `:ro`** — token refresh is in-memory only (verified 2026-05-11; if upstream changes write path, symptom is 401s + "Read-only file system" in logs).

**Baked container env:** `CRT_TEMP_DIR`, `CRT_STATE_FILE`, `CRT_YT_CLIENT_SECRETS`, `CRT_YT_TOKEN_FILE` are set in `docker/Dockerfile` (paths under `/data/`); keep them out of `.env`.

**Network:** the daemon listens on `0.0.0.0:8765`. The Chromecast fetches `/media/...` from Chet's LAN IP (chosen by `_get_local_ip()`); the Mac reaches it over the tailnet with `CRT_DAEMON_URL=http://chet.<tailnet>.ts.net:8765 crt-tui`. UFW is inactive on Chet: the Fritz!Box NAT is the only barrier to the internet.

**HTTP control surface** consumed by TUI + Flipper bridge: `GET /status`, `GET /library/items`, `POST /control/{next,prev,toggle,stop,loop/toggle,sync,calibrate,seek/back/{n},seek/forward/{n},delete/current}`. `delete/current` goes through `PlayerCore.delete_request`: playing deletes the video on air; with the screen shown it asks for confirmation on the highlighted row (red notice, only the next `toggle` deletes, any other key cancels, an explicit command cancels and still acts, and a second `delete/current` cancels too: a bridge retry never confirms); with the page closed it opens the stopped screen already asking. The ack carries `deleted_video_id` (the video deleted at once while playing, else null).

**OAuth bootstrap** (one-time, manual on Mac): `python -m crt.bootstrap` opens browser → writes `~/.local/share/crt-player/{client_secrets,oauth_token}.json`. `lodge crt-player install` validates these exist on the Mac then `scp`s them to `/opt/lodge/crt-player/secrets/` with `chmod 600`. As of v2 (2026-05-13) the OAuth scope is `youtube` (full read+write) instead of `youtube.readonly` — required so `/control/delete/current` can remove the item from the YouTube playlist. A scope-bumped re-bootstrap is required when upgrading from a v1 deployment: re-run `python -m crt.bootstrap` on the Mac, then `lodge crt-player install` (or `scp oauth_token.json` to `/opt/lodge/crt-player/secrets/`) and restart the container. **GCP consent screen must be in "Production" publishing status** (APIs & Services → OAuth consent screen → Publish) — "Testing"-mode apps with sensitive scopes (`auth/youtube`) get their refresh tokens revoked by Google after exactly 7 days, silently killing playlist sync. One-time config change; no code change needed.

**Deploy mechanics:** `lodge crt-player update` does `git reset --hard origin/main` on Chet → push local main before deploy. `lodge crt-flipper-bridge` has no `update` subcommand; `install` is idempotent (re-SCPs sources, rebuilds). `lodge ssh` is interactive-only (opens a TTY); for one-shot remote commands use direct `ssh flocca@chet.tailc1c72f.ts.net "<cmd>"` (daemon) or `ssh flocca@lodge.tailc1c72f.ts.net "<cmd>"` (bridge).

**Re-OAuth shortcut:** scope-only re-deploy after re-running `crt-bootstrap` on Mac doesn't need full `lodge crt-player install`: `scp ~/.local/share/crt-player/oauth_token.json flocca@chet.tailc1c72f.ts.net:/opt/lodge/crt-player/secrets/ && ssh flocca@chet.tailc1c72f.ts.net "chmod 600 /opt/lodge/crt-player/secrets/oauth_token.json && docker restart lodge-crt-player"`.

**Flipper command byte → HTTP endpoint** (in `../homelab/services/crt-flipper-bridge/bridge.py` COMMAND_TABLE): `0x01`→next, `0x02`→prev, `0x03`→toggle, `0x04`→stop, `0x05`→loop/toggle, `0x06`→sync, `0x07`→calibrate, `0x08`→seek/back/15, `0x09`→seek/forward/30, `0x0A`→delete/current. The bridge runs in Docker on Lodge (host network + `/run/dbus` mount + `NET_ADMIN`). When you add/rename a `/control/*` endpoint in this repo, mirror the change in the bridge's COMMAND_TABLE.

## Integration Tests

Tests in `tests/test_integration.py` exercise the full stack with a real Chromecast and real YouTube URLs. They are opt-in (`pytest -m integration`) and skip automatically if env vars are absent.
- Configure via `source .env.integration` (gitignored). Key vars: `TEST_CHROMECAST_NAME`, `TEST_VIDEO_URL_1`, `TEST_VIDEO_URL_2`, `TEST_ENCODE_WAIT_S` (default 600s), `TEST_PLAYBACK_WAIT_S` (default 300s).
- `fetch_title()` always runs before the encode cache check — queue item status stays `"queued"` until the network call returns. YouTube rate-limits back-to-back `extract_info` calls; allow up to `encode_wait_s` for "pipeline started".
- Session-scoped `real_chromecast` fixture must recreate `asyncio.Event` objects per test (different event loops). Teardown calls `quit_app()` so the next test starts from a closed receiver app.
- After a play, give the page a few seconds to load the video and report before asserting `current_time_s`: the first play answers `reason="launching"` at once and DashCast then takes up to `RECEIVER_CONNECT_TIMEOUT_S` (20 s) to open the page.

## Gotchas

- `crt.youtube_client.SCOPES` is the single source of truth for OAuth scope. `crt/bootstrap.py` and any future caller must `from crt.youtube_client import SCOPES`, NOT redefine locally. A stale duplicate in bootstrap.py caused a v2 re-OAuth to silently issue a readonly token (every `/control/delete/current` then 401'd and was swallowed by the player_core error handler — daemon stayed up, remote delete failed invisibly).
- **Watch Later (`WL`) as the playlist source was researched and abandoned (2026-10-15).** The Data API does not expose WL, and `CRT_YT_PLAYLIST_ID=WL` can return an empty snapshot that wipes the library and the cache. Read [docs/superpowers/specs/2026-10-15-watch-later-research.md](docs/superpowers/specs/2026-10-15-watch-later-research.md) before any work on Watch Later, YouTube account cookies, or a new playlist source.
- `_detect_crop()` can misidentify near-black scenes (dark opening titles, night shots) as letterbox and silently remove real pixels from the top/bottom of the source. Results in calibrated margins still appearing "too aggressive" on specific videos. Set `CRT_AUTO_CROP=0` to bypass.

- Calibration is a page state (`calibrating`), not a playlist item: `PlayerCore.calibrate()` pauses a playing video first (position saved), the page loops the clip in a second `<video>` (it takes the video decoder, so the return reloads `#main`: see the TV findings), and any key or 60 s returns to where it came from (the paused or the stopped screen). Its end never marks a video `done` and the periodic save sees position 0 (ignored). The clip is rendered once at daemon start (`prepare_calibration`, margins only change with a restart); before it is ready, or if ffmpeg failed, `calibrate()` only flashes "Calibrazione non pronta" on an open screen.
- Calibration pattern in `calibration.py` uses only `drawbox`/`drawgrid`, no `drawtext` — the Homebrew ffmpeg build here lacks libfreetype. Numeric margin values are surfaced to the user via a TUI toast in `action_calibrate` rather than overlaid on-screen.
- Textual `Binding` with letter keys (`s`, `p`, `q`) won't show in Footer and conflict with Input widget text entry. Use `ctrl+` combos with `priority=True` for global bindings — see `tui_client/ui.py` `BINDINGS` list.
- pychromecast commands (`launch_receiver`, `quit_app`, volume) can raise `RequestTimeout`/`RequestFailed` and block for up to 10s. Wrap them in `_safe_cmd` in `chromecast_mgr.py` and call them via `asyncio.to_thread()` from async code.
- **DashCast:** always `load_url(url, force=True)`; without `force` DashCast iframes the page inside its HTTPS shell and the HTTP page never loads (mixed content). Every `launch_receiver` restarts the app and shows the DashCast logo, so `PlayerCore._cast()` starts `_launch()` only when the page isn't connected or `receiver_app_active` is False. Commands never await the launch: they set the player's state and answer at once (the bridge times out at 5 s and retries, so a waiting command runs twice). `_launch()` waits for a *new* SSE subscriber (`wait_new_subscriber`), not a stale one left by a replaced page, and goes idle (`_drop_page`) if none comes.
- **`PlayerCore` transport commands never suspend** (`next`, `prev`, `play`, `toggle`, `stop`, `seek_relative`, `calibrate`: `async def` for the API, but every `await` inside reaches no real suspension point): a suspension let a later command run in the middle and act on a stale state, which three review rounds kept finding (Stop lost during a launch, calibration over a newer pause). Slow work runs elsewhere (`prepare_calibration` at startup, `_launch` in the background) and commands only read its result. Deletions too (`delete_current`, the screen's confirmed Elimina): the item leaves the library and the screen redraws at once on the loop, while the cache unlinks and the YouTube delete finish in a background task (`_delete_tasks`, failures only logged; shutdown waits for them up to `SHUTDOWN_DELETE_TIMEOUT_S`, 5 s, through `finish_deletes`); before, a slow YouTube call held the OK past the bridge's timeout and its retry resumed the successor.
- **Every new SSE subscription gets the whole player state** (`_on_receiver_connect`, fired by `ReceiverChannel.subscribe` each time, not only on the first): load + screen, calibration, or, while idle, `blank` + the stopped screen (on the cursor when the page was closed; never a bare `blank`). That is how a launched page, a reconnect after a blip, or a page that missed a Stop catches up; transport code just sends to whoever is subscribed.
- **`PlayerCore.live_position()` is the one source for "where are we now"** (`/status`, periodic save, shutdown flush). It reads `ReceiverChannel.live_position`, which the page's reports update and the channel extrapolates between them (at most `MAX_EXTRAPOLATION_S`, 3 s, past the last report, and frozen when the page disconnects); 0.0 while idle or calibrating. Every transition that leaves `playing`/`paused`, and every switch to another video, snapshots it onto the item first (`_snapshot_position`) — the issues #12/#13 rule (resume never restarts behind the real position) still holds.
- `PlayerCore._loaded_video_id` is the video the page holds; the cursor can move before the page changes video (the sync thread removes the cursor video, a pick during a relaunch). Position snapshots, `stop_and_remove`, the reconnect restore, `delete_current` while playing and the screen's delete confirm follow `_loaded_video_id`; the delete refuses when the cursor left the paused video.
- Seeks stop `SEEK_END_MARGIN_S` (0.5 s) short of the duration: at exactly `duration` the `<video>` resumes from 0 instead of ending.
- The receiver browser is Chrome 90 (CrKey 1.56, 1280x720 CSS px, devicePixelRatio 1.5): no `:has()`, container queries, `structuredClone`, top-level `await`. Everything drawn over the video sits in a 75%-wide box with `transform: scaleX(1.3333)` to undo the TV's 16:9→4:3 squeeze; check page changes on the real TV.
- `ReceiverChannel` drops `ended` and status reports whose `src` is not the URL of the last `load`: a late `ended` from the previous video must not advance the playlist. `watch_natural_end` also acts only while `playing`, and only if the src that ended is still `expected_src` when it wakes (a load may land in between).
- A `<video>` error reaches the daemon as `{event: "error", media: true}`: `PlayerCore._on_media_error` pauses with the screen and the notice "Errore nel video", and `toggle` on it reloads the file. Script and `play()` errors carry no `media` flag and are only logged.
- When the page's last SSE subscriber leaves, `PlayerCore` waits `RECEIVER_LOST_GRACE_S` (10 s): a reconnect within it re-sends `load` at the saved position (paused with the screen, or playing) without the logo; past it the player goes `idle` with the position saved. Another app taking the Chromecast ends the same way. While a launch is pending the timer waits for it to end and then checks `connected`: the launch and the timer never decide separately.
- On app exit and on idle close, `ChromecastManager.quit_app()` closes DashCast so the TV leaves the page. Stop keeps the app open on the stopped screen (so the next play has no logo); the page is left only by Spegni, the idle close, app exit, or another app taking the Chromecast.
- `PlayerCore._launch()` must `await chromecast.wait_for_connection()` before launching the page: restored `"ready"` items can be played before discovery completes.
- Textual `Static.render()` text is not clickable (applies to `tui_client/ui.py`). Any interactive element must be a real `Button` widget inside `compose()`; events bubble up via `on_button_pressed`.
- Chromecast always outputs a 16:9 signal. Sending a 4:3 file results in pillarboxing. Encode to 16:9 (1024x576) with stretched 4:3 content so the user's HW squeeze restores correct proportions. This is handled by `_build_video_filter()`.
- YouTube videos often have black bars baked into the pixel data (pillarbox/letterbox). `_detect_crop()` handles this automatically. Without it, crop/scale operates on the bars as if they were content.
- `active_item()` returns the first item matching `ACTIVE_STATUSES` (which includes "ready"). To find the playing item specifically, use `next((i for i in queue.items if i.status == "playing"), None)` — avoids picking a "ready" item that sits earlier in the queue.
- Textual `Static` with overridden `render()` doesn't update the widget's internal `_content` size cache (applies to `tui_client/ui.py`). Use `watch_*` reactive methods that call `self.update(...)` instead — otherwise title changes may render from stale content and `height: auto` won't adapt.
- Running scripts standalone (outside `./run.sh`) needs `set -a; source .env; set +a` before `python ...` — the `.env` file has no `export` prefix, so a plain `source` only sets shell-local vars and Python won't see them.
- The `flipper_app/` Flipper FAP is its own subproject: `ufbt` SDK, no Python tests. Spec: `docs/superpowers/specs/2026-05-10-flipper-remote-design.md`. Uses a forked Serial profile (Momentum FW source in `flipper_app/libs/serial_profile.{c,h}`) with custom `mac_xor` to bypass the firmware's BtSrv RPC handler — without that, button TX is silently dropped. Pairs with the bridge in `../homelab/services/crt-flipper-bridge/`. Detailed subproject guidance: [flipper_app/CLAUDE.md](flipper_app/CLAUDE.md).
- Don't add `sources=` to a Flipper `application.fam` if you have subdirs: ufbt auto-discovery is recursive, and explicit globs (`["*.c", "libs/*.c"]`) cause duplicate-definition link errors.

- TV findings for the teletext page (Chrome 90 on the Chromecast; check page changes on the real TV): the Chromecast has **one hardware video decoder**. When `#preview` or `#cal` loads a file, `#main`'s pipeline is revoked and keeps answering as if healthy while it shows and plays nothing (black, silent, position barely moving) until reloaded: the page marks it (`mainStale`, holding the paused position, or a pending load's target while its metadata is on the way) and reloads it from the same file on the paused row's background, at night, on `play` and on a same-file `load` (about 1 s of black on the paused row). A paused load paints no frame until a muted play/pause (`primeFrame`, status reports suppressed meanwhile), and it is muted before `load()`: muting just before the priming play lets a fraction of audio out. `muted` is ignored on a second `<video>` that has audio, hence the audio-less preview copies; a hidden `<video>` showed its last frame on the video plane, so the preview is unloaded (`removeAttribute("src")` + `load()`), never just hidden (both seen before the decoder limit was known, possibly the same cause). No CSS animation over video at 24-30 fps (it stutters): the snow is a 160x90 canvas redrawn by a timer.
